# 文体骨架：学习路径

> 本文归属的规则：**WRT-LP-nn** ｜ 来源与许可见文末 §6
> 规则 ID 构成：`WRT-LP-<级别字母><两位序号>`。级别字母 = `S`(`structural_invariant`) / `R`(`reviewed_invariant`) / `C`(`craft_default`) / `T`(`taste_option`)，与 `规则契约.md` §0 的四级判定者表一致。
> 本文件是规则正文的**唯一处**：其它文件只许引 ID，不许复述条文。
> **每条规则行末带四字段**：`〔源键｜依据类型｜版本与实施日期｜适用文体〕`。
> ⚠️ 纪律：以下条文都是**我们自己的话**。来源的逐字引用只出现在 §6，每个来源 ≤1 句。

## 0. 适用与不适用

**用这个骨架**（条件）：产物是**一条从零到会用的学习路径**——它同时给出**推荐阅读顺序**与**可执行的实测案例**，读者按这个顺序把案例做完，就覆盖了要教的所有东西。典型形态：插件/框架/平台的上手课、系列教程的总目录与各章、内部新人培训手册、一本书的课程化版本。

**不用这个骨架**：

| 情形 | 为什么不用 | 换成 |
| --- | --- | --- |
| 只教"完成一件具体的事" | 那是单篇教程的活，不承诺覆盖，也不需要顺序 | `文体-技术文章.md`（教程型）或 `文体-README.md` |
| 产物是 API / 配置 / 命令的完整清单 | 参考材料不排序、不承诺"学完" | 参考文档 |
| 只讲一个系统为什么这样设计 | 读者要的是理解，不是路径 | `文体-技术文章.md`（深潜型） |
| 目录页，只有链接 | 没有案例就没有"学"；只有链接的目录是导航，不是路径 | 站点导航 / `README` 的文档表 |
| 学习计划（时间表、打卡） | 本骨架管"读什么、做什么、怎么算学会"，不管日程 | 另定骨架 |

### 0.1 与其它文体的边界（一句话）

- **技术文章**回答"这个东西怎么工作/为什么这样"；**学习路径**回答"我要按什么顺序做什么，才学会它"。
- **README** 是"这一页让人决定用不用"；**学习路径**是"决定用之后，接下来三十天做什么"。
- **参考文档**是"查"；**学习路径**是"走"。三者可以互链，但不能互相冒充。

## 1. 这份骨架承诺什么

**学习路径 = 顺序 + 可执行案例 + 覆盖承诺 + 验收**。四样缺一，就不是学习路径，而是一堆排过序的文章。

| 要素 | 判据 | 缺了会怎样 |
| --- | --- | --- |
| **顺序** | 每一章的位置有**依赖理由**：不先做前一章，这一章做不下去 | 读者按目录读，在第 4 章卡死 |
| **可执行案例** | 每章至少一个**实测过**的最小案例：命令、预期输出、失败形态 | 读者"看懂了"，动手全错 |
| **覆盖承诺** | 一张**能力 × 章节**的覆盖矩阵，承诺的每项能力至少一章 | "学完所有"无法验证，也没人知道漏了什么 |
| **验收** | 每章一个**可观察**的完成判据（跑出什么、看到什么） | 读者不知道自己该不该往下走 |

> ⛔ **最常见的失败形态不是"写得不好"，而是"顺序是采集顺序"**：作者按自己调研/实现的先后排章，读者按这个顺序走必然在依赖上断裂。所以顺序必须是**读者依赖顺序**，不是作者时间顺序（→ `WRT-LP-R01`）。

## 2. 结构骨架

### 2.1 开篇：三样东西，一屏之内

1. **学完能得到什么**（能力清单，可验证的动词句）
2. **不教什么**（边界，防止读者期待错位）
3. **路径总表**——读者只看这一屏就能决定跟不跟：

| # | 章节 | 前置 | 你会做出什么 | 完成判据 | 实测案例 | 预计耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | … | 无 | … | 命令 + 预期输出 | `案例 1-A` | 15 min |
| 2 | … | 第 1 章 | … | … | `案例 2-A` | 30 min |

- **前置**一列只能填"无"或前面出现过的章节号；填不出来说明顺序错了。
- **完成判据**一列必须能被旁观者验证（跑出什么、文件里有什么），不能写"理解了"。
- **实测案例**一列填案例编号，正文里要有同名小节。

### 2.2 前置与环境

在第一章之前单独一节，声明四件事：**版本**（工具/引擎/依赖的精确版本）、**平台**、**依赖**（要预装的）、**起点目录**（读者从哪个空目录/空项目开始）。缺任何一项，案例都不可复现（→ `WRT-LP-S08`）。

另外，如果这个工具/插件**需要先配置才能跑**（路径、地址、密钥、必填项），前置一节还要给一张**必填配置表**：
每行写「项名 / 填什么 / 空着会怎样 / 怎么检查」。**不要把这些值只塞进代码块让读者照抄** ——
照抄的人一旦漏了一项，会在第一条命令上撞见一句看不懂的报错（→ `WRT-LP-R11`）。

> ⚠️ **只讲"缺了会挡住第一步"的那几项，不要罗列全部配置。** 本规则不是"配置手册"，
> 是"别让读者在第二步卡死"。全部配置的清单交给参考页。

### 2.3 每章骨架（七段，顺序固定）

| # | 段 | 写什么 | 为什么在这个位置 |
| --- | --- | --- | --- |
| 1 | **本章产出** | 一句话："本章结束，你会有一个 X" | 读者先知道终点，才愿意走 |
| 2 | **前置检查** | 一条命令验证上一章的产物还在 | 把"环境坏了"和"本章学不会"分开 |
| 3 | **最小可跑案例** | 编号案例：**在哪输入** / 命令 / **输出在哪** / 预期输出 / 失败形态；**关键选择要写 why**（→ `WRT-LP-R14`） | **先跑再解释**：跑通给信心，输出给证据。**缺"在哪输入/输出在哪"，读者一定卡住**（→ `WRT-LP-S09`） |
| 4 | **它为什么这样工作** | 只解释案例里出现的东西 | 没有案例的解释是背诵 |
| 5 | **常见失败** | 表：症状 / 原因 / 修 | 把坑集中，别散在正文里 |
| 6 | **自测** | 2–3 个"改一下还能跑吗"的问题 | 验证不是抄命令 |
| 7 | **下一章钩子** | 一句话：下一章要用到本章的什么 | 顺序的依赖理由在这里显性化 |

#### 2.3.1 每个命令块都要回答的三个问题

命令不是"贴上去就行"的。一条命令要让**没看过作者机器**的读者跑通，必须同时写清：

| 问题 | 为什么必须写 | 写法 |
| --- | --- | --- |
| **在哪输入** | 同一个字符串，输在终端、应用内控制台、编辑器输入框里是三个不同结果；输错地方通常**没有任何报错** | 明确写「Windows 终端（PowerShell/CMD）」/「应用内控制台（怎么打开，例如"有视口的游戏窗口按 `~`"）」/「GUI 的某个菜单」 |
| **输出在哪** | 命令行工具常常**不回显**，结果写进日志/文件；读者看不到就以为命令无效 | 写清「哪个窗口 / 哪个文件 / 哪个界面元素」，并给出该行开头的前缀，例如 `[Status] event=Snapshot` |
| **预期长什么样** | "没有反应"和"失败了"在读者眼里长得一样 | 给一段**可对照的样例**（真实日志行/文件内容/界面截图描述），允许 `<id>` 之类占位 |

> ⚠️ **这三问不是给新手的糖，是给作者的验收线。** 真实事故：文档写「在控制台输入 `X.Status`」，
> 读者先在 Windows 终端里敲（不是命令）、再在编辑器的 Cmd 输入框里敲（世界不对，函数直接 return）——
> 两次都"没有反应"，而文档全程没写输出会去哪。**根因就是这三问缺了两问。**


### 2.4 覆盖矩阵（放在末尾，或紧跟路径表）

矩阵的行是**用户会用的功能组**（他能点名要的那一块），不是章节号，也不是 API 清单：

| 功能组（学完能做的事） | 章节 | 验证方式 |
| --- | --- | --- |
| 起一个本地实例 | 1 | 跑 `案例 1-A` |
| 接一个客户端 | 2 | … |
| 组队 | 5 | … |

- 行数不得少于开篇承诺的条数（→ `WRT-LP-R03`）；行要按**功能组**列（→ `WRT-LP-R13`）。
- 必须有一节"**没有覆盖什么**"，把明确不教的东西列出来——**缺口要显式，不能靠读者自己发现**。

### 2.5 附录

命令速查（**不重复正文**，只汇总）、术语表（首次出现处已定义，这里只是索引）、参考资料（外部链接）。

## 3. 规则

### 3.1 `structural_invariant`（脚本可阻断）

| `WRT-LP-S08` | structural_invariant | 条件是第一章之前 → 要求**前置与环境**一节声明四件：版本、平台、依赖、起点目录 → 缺任一即 major。 〔GW｜一手（官方课程）｜抓取 2026-11-11｜学习路径〕 |

| ID | Class | Knowledge |
| --- | --- | --- |
| `WRT-LP-R01` | reviewed_invariant | 条件是任意两章相邻 → 要求后一章的**前置**只能引用前面出现过的章节或"无"，且能说出**依赖的是上一章的哪个具体产物**（文件、进程、账号、配置行）→ 只写"建议按顺序"不算顺序理由。 〔RM｜本轮推导｜2026-11-11｜学习路径〕 |

| `WRT-LP-R10` | reviewed_invariant | 条件是写了「预期输出」→ 要求给**可对照的真实样例**（日志行、文件内容、界面元素），允许 `<id>`/`<端口>` 之类占位；只写"运行成功""输出正确""能看到结果"即不合格。 〔RM｜本轮推导｜2026-11-11｜学习路径〕 |
